Result: **every earlier finding is closed** (volume staleness, `device_name`/malformed `/pair`, `ip` refresh, version test, volume-event test, order of checks). **No breaking mismatches and none between the two projects.** What remains is one real order-of-checks bug in the agent, one smaller agent mismatch, one small app gap, a few missing tests, and three small contract decisions. Nothing breaks the apps in normal use. I did not run `cargo test` or `flutter test`.

## desktop-agent
- [ ] #1 `src/api/library.rs:105-123` - `POST /play/track` order of checks (C-004: `401 → 400 → 409/501 → 404`) - expected: with Apple Music closed, a valid song link answers `409 APPLE_MUSIC_NOT_RUNNING` whether or not the catalog knows the song; actual: the handler does the catalog lookup first (`lookup_track(...)` → `404`, or `500` with no internet) and only then calls `media.play_track(...)`, where the window check happens. So Apple Music closed plus an unknown song gives `404`, and closed plus no internet gives `500`. Tests cover closed (song always known) and 404 (Apple Music always running), not the combinations. `/play/playlist` follows the order correctly. *(Confirmed by hand.)* **Fix:** check that Apple Music's window exists before the lookup, or settle it in the contract (see gaps).
- [ ] #2 `src/api/player.rs:74` and `src/api/library.rs:105` - failed media backend - expected: "media calls answer `500 INTERNAL`" when the agent's own backend failed to start; actual: `POST /player/seek` answers `409` (`apple_music_running()` is false on `NullBackend`) and `POST /play/track` answers `501` (`ui_supported()` is false). Transport, volume, playlists and play-playlist do answer `500`. Low. *(Confirmed by hand for seek.)*
- [ ] #3 missing tests (low): `NullBackend` behaviour outside `main.rs`; no-body / wrong-content-type `400` for `POST /volume`, `/player/seek` and `/play/track` (only `/pair` and `/play/playlist` are covered; all use the same extractor); `q=a+b` (space as `+`; only `%20` is tested); `{"muted":null}`; discovery thread wiring (`discovery.rs:130-179`: the `ip` decision logic is well tested, the real re-announce is not — a line in `docs/smoke-tests/mvp-0.md` would cover it).

## Contract gaps — all settled in C-005 (documentation only; no code change needed)
- [ ] **`POST /play/track` and the order of checks.** The contract puts `409` before `404`, but the agent must look the song up first (it needs the title to drive the window), then check the window. Decide: the agent checks the window first (code change), or the contract says that for `/play/track` the catalog lookup (`404`, and `500` offline) comes before the `409`.
- [ ] **`501` versus `409`.** The agent answers `501` (UI Automation unavailable) before `409` and tests it; the contract lists "`409`/`501`" as one tier without saying which wins.
- [ ] **What counts as a "media call" when the backend failed.** Say whether seek and `/play/*` answer `500` too (the agent's current code does not).
- [ ] **First-pairing fallback.** See #4: say whether the resolver fallback applies when pairing, or only to a saved session.
