# Contract conformance report
Date: 2026-11-15 · Checked up to MVP 4 · Contract at C-006 (both projects applied C-006) · Agent code: yes · App code: yes

Result: **no breaking mismatches and none between the two projects' wire formats.** The seven new samples round-trip in both projects, the new routes, check order, `modes` event and connect order match, and the legacy `/search` and `/play/track` are unchanged. What remains is one small app bug, one agent status-code deviation (rare), and four small contract decisions. I did not run `cargo test` or `flutter test`. This check looked at the MVP 4 surface; the older backlog items from the C-004 report (the agent `NullBackend` / seek / play-track edge cases, discovery fallback when pairing, a few missing tests) were **not re-checked individually**, so treat the previous report's remaining items as still open until a project ticks them.

## desktop-agent
- [ ] #1 `src/media/uia.rs:1386-1390` (`Uia::ask`) - `GET /app-search`: "`500` if the app did not answer in time" - expected `500 INTERNAL` when Apple Music does not answer in time; actual: the outer 35 s `OP_TIMEOUT` returns `MediaError::NotSupported("Apple Music took too long to respond")`, mapped to `501` (`api/mod.rs:166`). The inner search timeout (`UiaError::Unchanged`, 12 s) correctly gives `500`, so the `501` shows only when the UI Automation thread is stuck or waiting behind other calls. The same path serves modes, queue and `/queue/play`. Low, rare. *(Confirmed by the skeptic.)* **Fix:** map the outer timeout to `Internal` (and say so in the contract, see gaps).

## android-controller
- [ ] #2 `lib/features/search/search_controller.dart:134` and `:171` (`setQuery`, `submit`) - `q` is 2-200 characters after trimming - expected: the app counts characters like the agent (`chars().count()`, Unicode scalars); actual: `query.length < minQueryLength` counts UTF-16 units, so a one-character query that is an emoji passes in the app and the agent answers `400`. The user sees the generic error state with a retry that fails again. The 200 cap already uses `.runes`. Very low. *(Confirmed by the skeptic.)* **Fix:** use `query.runes.length` for the minimum too, and add a test with one emoji.

## Contract gaps — all settled in C-007 (documentation; finding #1 is the only code change it asks for)
- [ ] **Timeout code for window-driving calls.** `GET /app-search` is documented as `500` on timeout, but `/player/modes`, `/queue` and `/queue/play` say nothing. Say that an Apple Music timeout on any UI Automation call is `500 INTERNAL` (this also settles #1).
- [ ] **Unknown values on the client side.** The contract does not say what a client does with an unknown `repeat` (in `GET /player/modes` or the `modes` event), `QueueItem.source` or `AppSearchResult.kind`. The app maps unknown `repeat` to `off`, unknown `source` to `queue`, and keeps `kind` as a free string. Say that clients do this.
- [ ] **Blank and trimmed text.** `title` and `section` are "non-empty string". The agent trims them, rejects blanks with `400`, and matches on the trimmed text (`api/mvp4.rs:116-124`); the app does not trim. Say "non-empty after trimming" and that matching ignores surrounding spaces.
- [ ] **`modes` after Apple Music comes back, and when the read times out.** The agent keeps its last modes across a gap and sends nothing after Apple Music restarts with the same values, and it skips the connect `modes` when the read times out (1.5 s). The app copes by calling `GET /player/modes` on start, on `apple_music` becoming true, and after a reconnect. Say that a client must do this, because the `modes` event is not guaranteed to follow.

## Verified as matching (MVP 4)
- **HTTP (agent):** all six new routes and methods; `204` vs `200`; snake_case names and lowercase enums; order `401 → 400 → 501 → 409 → 404` (`/queue/play` re-reads the queue, so `409` comes before the title `404`); legacy `/search` and `/play/track` untouched.
- **HTTP (app):** Bearer on everything except `/pair`; `204` never decoded; errors mapped by code, an unknown code is `INTERNAL`; `/queue/play` and `/app-search/play` wait 45 s; `scope` sent as `catalog` or `library`; blank `title`/`section` never sent; unknown `repeat` becomes `off`.
- **WebSocket:** envelope and the five event names on both sides; connect order `state`, `apple_music`, `volume` (audio session only), `modes` (readable only); lag resend includes `modes` and is tested; `modes` pushed only on a real change (2 s read, nothing sent when the buttons are unreadable), tested; no `queue` event, and the app re-reads `GET /queue` on title or `artwork_rev` change, after a modes change, on open, on pull-to-refresh and after a reconnect, with no timer; stale modes are cleared on a pushed event; unknown event types are ignored; ping 15 s / pong, 45 s idle close.
- **Discovery and 401:** `_amremote._tcp`, port 8765, TXT `version`, `name`, `ip` on both sides; `401` sends the app back to pairing. (Pairing code on the agent side was not read in this check.)
- **Samples:** all 35 round-trip in both projects (the 7 new ones: `modes_response`, `modes_request`, `queue_response`, `queue_play_request`, `app_search_response`, `app_search_play_request`, `ws_modes`).

## Rejected as false alarms
- Agent `scope` leniency: `GET /app-search` trims and lowercases `scope` while `POST /app-search/play` is strict. The contract only says "`catalog` or `library`", so both are allowed. (Not a finding.)
