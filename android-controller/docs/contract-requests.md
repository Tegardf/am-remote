# Contract requests (android-controller)

Gaps found while building. The root window settles them with `/contract-change requests`; this window then applies the result with `/sync-contract`.

- [x] The contract should say how the app gets the agent's IPv4 address from mDNS: add a TXT field (for example `ip=<ipv4>`), or require the agent to listen dual-stack on `[::]` - why: on an Android emulator (2026-11-14) NSD resolved the laptop only to the IPv6 link-local address `fe80::…%wlan0`, while the agent listens on `0.0.0.0:8765` (IPv4 only), so a discovered agent can't be reached - default used: discovered services whose host is only an IPv6 literal are skipped, so the user must use "Enter IP manually" (MVP 0, 2026-11-14)
- [x] The contract should say what the app does when mDNS TXT `version` is missing or not `1` (list it anyway, warn, or hide it) - why: the TXT `version` is read but nothing in the contract says what to do with it - default used: every discovered agent is listed and pairable, `version` is stored on `DiscoveredAgent` and otherwise ignored (MVP 0, 2026-11-14)
- [x] The contract should say whether `GET /volume`, `POST /volume` and the transport commands answer `409 APPLE_MUSIC_NOT_RUNNING` when Apple Music is closed, and what `GET /volume` returns before Apple Music has played anything (related to open question #3 in `../contract/README.md`) - why: the empty state depends on it - default used: a 409 from any of these calls shows the "Open Apple Music on your laptop" empty state; any other volume error leaves the slider disabled and shows nothing (MVP 1, 2026-11-14)
- [x] The contract should say how `POST /volume` treats a `level` outside 0-100 and an empty body `{}` (clamp, ignore or error), and which code a bad request body gets (related to open question #1, `BAD_REQUEST` 400) - why: the app can't know whether to expect an error - default used: the app only ever sends a level clamped to 0-100 and always at least one field; an unknown error code is treated as INTERNAL (MVP 1, 2026-11-14)
- [x] The contract should say whether the agent pushes a `state` message right after `POST /player/seek`, and whether it pushes position updates while playing or only on change - why: the progress bar interpolates between pushes and uses the next `state` to confirm a seek - default used: the bar advances on its own every 250 ms while playing; a seek target is shown until a push whose position is within 3 s of it arrives, or for 2 s at most (MVP 2, 2026-11-14)
- [x] The contract should say what `GET /player/state` and `GET /player/artwork` answer when Apple Music is closed or idle, and which errors `/player/artwork` can give besides `404` (409? 500?) - why: the app must tell "no artwork" from "try again" (related to open question #2, the empty `PlayerState`) - default used: only `404` means "no artwork" (placeholder); any other failure keeps the old picture and asks again on a later push, at most every 5 s; a missing or null text or number field in `PlayerState` becomes `""` or `0`; a `409` from `GET /player/state` sets "Apple Music not running" (MVP 2, 2026-11-14)
- [x] The contract should say what `GET /playlists`, `GET /search`, `POST /play/playlist` and `POST /play/track` answer in each failure: `501 NOT_SUPPORTED` when the agent can't read playlists or search (and whether search can be supported while playlists are not), `409 APPLE_MUSIC_NOT_RUNNING`, and a bad request (an empty or one-letter `q`, an unknown playlist `id`, a `url` that is not a `music.apple.com` link) - why: the screens show a different message for each and the contract only lists the codes - default used: `NOT_SUPPORTED` shows "isn't available on this laptop yet" and no error, `APPLE_MUSIC_NOT_RUNNING` shows "Open Apple Music on your laptop", anything else (including an unknown code or a malformed answer) shows a generic "Couldn't …" with Retry; the app sends `q` only with at least 2 characters and plays a result with its own `url` untouched (MVP 3, 2026-11-14)
- [x] The contract should say how many results `GET /search` may return and in what order, whether `limit` has a maximum, and how `q` is encoded (the app sends form encoding: a space is `+`) - why: the list shows what it gets, with no paging - default used: `limit=25` is always sent and the list is shown in the order received (MVP 3, 2026-11-14)
- [x] The contract should settle open question #4 (`artwork_url` is an internet HTTPS URL, but the app was meant to have no internet traffic) - why: search thumbnails need it - default used: the app loads `artwork_url` itself, over HTTPS only, through its own loader: it refuses `http://`, refuses a redirect to anything but `https://`, sends no token or header, drops pictures over 2 MB, and keeps 80 in memory; if the agent proxied the artwork instead (for example `GET /search/artwork`), the app could drop internet access entirely (MVP 3, 2026-11-14)
- [x] The contract should say how a bad token is signalled on the WebSocket handshake (HTTP `401` on the upgrade, or a close code) - why: the app can't read the status of a failed upgrade reliably - default used: a dropped socket triggers an immediate `GET /status`, and its `401` sends the app back to pairing (MVP 2, 2026-11-14)
